# Let services save, let restic store

Yes: reframe backup as **stack snapshots**, have each service template declare a **paired `save`/`restore`** procedure, and adopt **restic ≥ 0.19.1 wholesale as the storage engine**, but not as an orchestrator (restic has none, which is why it fits). "Snapshot" is the right noun. restic, kopia, Elasticsearch/OpenSearch and Neon all use it for what Angee already produces: an immutable, named, non-atomic record in a repository. The docs should say what Elasticsearch says, that a snapshot "doesn't represent a cluster at a precise point in time" ([Elastic](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore)). Every hook design that has lasted pairs backup with restore: BOSH BBR, YunoHost, StartOS, KubeStash, Kanister and borgmatic. The one well-known system that streams dumps without a restore counterpart, K8up, says outright "You can't restore from backups that were done from `stdin`" ([K8up](https://docs.k8up.io/k8up/how-tos/restore.html)). Restore should always land in **empty state**. "Init a new stack from a snapshot" becomes the main path, as it is in RDS, DigitalOcean, YunoHost, StartOS and Cloudron. In-place restore is the same pipeline, run after a safety snapshot and with the old state moved aside. restic beats kopia and borg because it owns only storage: repository, encryption, dedup, backends, retention, verification and byte-level restore. You drive it through a documented JSON and exit-code contract, and its maintainers say "the only interface we have is the binary" ([restic #1089](https://github.com/restic/restic/issues/1089)). Kopia's actions and policies, and borg's companion borgmatic, would duplicate Angee's hook layer. Kopia's Go packages are unstable enough that Velero and Kanister pin forks. Borg 2.0 is still a beta that broke repositories in September 2026. The research also found **three defects in today's v0.23.0 capture**, all detailed in the database section: the `pg_dump` flags `--no-owner --no-acl` do nothing, the `pg_restore --list` check proves little, and the live file-by-file copy is unsafe for SQLite WAL databases and Redis AOF directories.

## "Snapshot" already names Angee's artifact among its peers

"Snapshot" has two established meanings, and Angee's artifact fits only one of them. The first is the **storage-level copy-on-write image**. ZFS snapshots "are created atomically" ([OpenZFS](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-snapshot.8.html)). EBS snapshots are point-in-time, but AWS still recommends that "you pause writes to the volume before you create the snapshot" ([AWS EBS](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-creating-snapshot.html)). Kubernetes CSI and Fly volumes use the word the same way. Azure's taxonomy is the honest summary: without app-level quiescing, such snapshots are at best crash-consistent ([Azure Backup](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-introduction)). The second meaning is a **named, immutable record of one backup run inside a repository**, and atomicity is not implied. Elasticsearch states that "a snapshot doesn't represent a cluster at a precise point in time", yet calls taking one "the only reliable and supported way to back up a cluster" ([Elastic](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore)). OpenSearch adds that snapshots "aren't instantaneous" ([OpenSearch](https://docs.opensearch.org/latest/tuning-your-cluster/availability-and-recovery/snapshots/snapshot-restore/)). restic's unit is literally "called a 'snapshot'" even though it is a file walk ([restic](https://restic.readthedocs.io/en/stable/040_backup.html)), and kopia calls each run a "point-in-time backup" snapshot ([kopia](https://kopia.io/docs/getting-started/)). A `pg_dump` plus selected persist files plus a recovery manifest is exactly that second kind of object.

The case for keeping "backup" is real. **"Backup" dominates managed databases and DR products**: Heroku PGBackups, RDS automated backups, Render, Railway, DigitalOcean, Supabase, Velero and Proxmox all use it ([RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html), [Velero](https://velero.io/docs/main/restore-reference/)). Home Assistant went the opposite way to the proposal: its `snapshot`, `snapshot_pre` and `snapshot_exclude` keys survive only as legacy aliases of `backup*` ([Home Assistant](https://contributors.home-assistant.io/apps/reference/configuration/)). Angee's current verb, `capture`, has one strong precedent, Heroku's `pg:backups:capture`, and even there the noun stays "backup" ([Heroku](https://devcenter.heroku.com/articles/heroku-postgres-backups)). Systems that use both words split them by layer or by lifecycle. RDS keeps retention-bound "automated backups" next to manual snapshots that "don't expire" ([RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)). In Velero, a backup *contains* volume snapshots ([Velero FSB](https://velero.io/docs/main/file-system-backup/)).

Two arguments favour "snapshot" for Angee. First, **engine alignment removes a translation layer**. Once restic owns storage, every stored record *is* a restic snapshot, `restic backup` is the command that creates one, and `angee snapshot list` becomes a filtered `restic snapshots`. Calling the same object a "backup" in Angee would mean translating terms in every message, flag and log line. Second, "snapshot" is more honest about where the data lives. The famous warnings ("A snapshot is not a backup" from [btrfs](https://btrfs.readthedocs.io/en/latest/Subvolumes.html), "Do not use VMware snapshots as backups" from [Broadcom](https://knowledge.broadcom.com/external/article?legacyId=1025279)) are about copies kept on the same media, not about consistency. A restic repository on the stack's own disk has the same weakness; Cloudron tells users not to store backups on the same server ([Cloudron](https://docs.cloudron.io/backups/)). The vocabulary "a snapshot lives in a repository, and becomes a backup when that repository is off-host" says exactly that. The cost is the block-level connotation. Pay it once, in the docs: say that an Angee snapshot is per-service consistent, not cross-service atomic, unless writers are held.

Some verbs should stay out. "Rollback" means in-place destruction in ZFS (`zfs rollback` destroys newer state) but provisions a *new* database at Heroku ([OpenZFS](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-rollback.8.html), [Heroku](https://devcenter.heroku.com/articles/heroku-postgres-rollback)). "Checkpoint" means frozen process memory (CRIU, Podman) ([Podman](https://docs.podman.io/en/latest/markdown/podman-container-checkpoint.1.html)). "Save/load" means Docker images ([Docker](https://docs.docker.com/reference/cli/docker/image/save/)). "Export/import" fits the one case where a portable plaintext file is handed to a person. There is also a local collision the research did not cover: jj, which Angee now drives, calls its automatic working-copy commits snapshots. Wherever the two could be confused, logs should say "stack snapshot".

## Every durable hook design pairs save with restore

There are three models for letting apps influence backup. **App-declared hooks** are BOSH BBR scripts, YunoHost scripts, StartOS manifests and SDK builders, and Juju actions. In **platform-owned dumps per database type**, Cloudron addons, Dokku plugins and Coolify dump the database for the app. In **platform capture tuned by app hints**, Home Assistant's hot/cold mode, pre/post commands and excludes, or Umbrel's `backupIgnore` globs, adjust a copy the platform makes ([Umbrel schema](https://github.com/getumbrel/umbrel/blob/HEAD/packages/umbreld/source/modules/apps/schema.ts)). Angee v0.23.0 is already a hybrid of the first and third: a trusted `capture:` job dumps into an operator-chosen directory, and `persist.<name>.backup: exclude` works like Umbrel's ignore list. What it lacks, compared with every mature system, is a declared restore counterpart, a quiescence declaration, and a safe failure contract.

The app-declared systems show what a complete contract looks like. **BBR** has each job ship up to seven executables under `bin/bbr/`: lock, backup and unlock for each direction, plus `metadata`. It runs them in three global phases: all `pre-backup-lock`, then all `backup`, then all `post-backup-unlock`. Data moves through `$BBR_ARTIFACT_DIRECTORY`. Before a restore, BBR validates checksums and checks that "the backup structure matches the deployment" ([BBR guide](https://docs.cloudfoundry.org/bbr/bbr-devguide.html)). The unlock script always runs and learns how the backup went through `BBR_AFTER_BACKUP_SCRIPTS_SUCCESSFUL` ([BBR source](https://github.com/cloudfoundry/bosh-backup-and-restore/blob/HEAD/instance/job.go)). **YunoHost** splits responsibility cleanly. `ynh_backup` only *declares* paths in a CSV, and the core builds the archive ([helpers](https://github.com/YunoHost/yunohost/blob/HEAD/helpers/helpers.v2.1.d/backup)). The restore script should be "a symetric version of what happens in the install script" ([example_ynh](https://github.com/YunoHost/example_ynh/blob/HEAD/scripts/restore)). **StartOS 0.4** states the rule bluntly: "Every StartOS package must define a backup strategy". It always stops the service during a backup ([recipe-backups](https://github.com/Start9Labs/start-technologies/blob/master/projects/start-sdk/docs/src/recipe-backups.md)). It also replaced 0.3's free-form docker actions with typed builders. `withPgDump` exists because rsyncing raw PGDATA is "slow and error-prone"; on restore it runs `initdb` on a fresh data directory and then `pg_restore --no-owner --no-privileges` ([StartOS Backups.ts](https://github.com/Start9Labs/start-technologies/blob/master/projects/start-sdk/lib/backup/Backups.ts)). The same code records a hard-won lesson: `pg_dump` once wrote a **0-byte file and still exited 0** on a FUSE mount, so a zero exit is not proof of an artifact.

Kubernetes operators show the cost of asymmetry. **Velero** hooks only *prepare* state (fsfreeze, flushes), and the bytes move through volume snapshots or file-system backup ([Velero hooks](https://velero.io/docs/main/backup-hooks/)). Its defaults are a warning to anyone copying it. Backup hooks default to `on-error: Fail`, restore exec hooks default to `Continue`, and an unset restore `wait-timeout` waits forever ([Velero restore hooks](https://velero.io/docs/main/restore-hooks/)). That infinite wait was only bounded in v1.19-rc.1 (#10280) ([Velero v1.19.0-rc.1](https://github.com/vmware-tanzu/velero/releases/tag/v1.19.0-rc.1)). **K8up** gets backup streaming right: it execs the pod's `k8up.io/backupcommand` and pipes stdout into `restic --stdin` ([K8up](https://docs.k8up.io/k8up/how-tos/application-aware-backups.html)). With no restore annotation, though, those backups can only be restored by hand with the restic CLI ([K8up restore](https://docs.k8up.io/k8up/how-tos/restore.html)). **KubeStash** fixes this by pairing tasks by name in each Addon, for example `logical-backup` ↔ `logical-backup-restore` ([KubeStash Addon](https://kubestash.com/docs/latest/concepts/crds/addon/)). **Kanister** goes further and passes the backup's `outputArtifacts` into the restore and delete actions as inputs ([Kanister](https://docs.kanister.io/architecture.html)). In the Compose world, backup-bot-two is the only tool surveyed with per-service `backupbot.restore.pre-hook`/`post-hook` labels ([backup-bot-two](https://git.coopcloud.tech/coop-cloud/backup-bot-two)). offen and resticker leave restore manual, and autorestic users have filed an issue asking for restore hooks ([autorestic #173](https://github.com/cupcakearmy/autorestic/issues/173)). The research found no Compose-spec convention for any of this.

borgmatic is the most complete "declarative source, tool-owned dump and restore" design. A `postgresql_databases` entry implies both `pg_dump` and `pg_restore`. Dumps stream through named pipes into Borg, so no plaintext touches disk ([borgmatic](https://torsion.org/borgmatic/how-to/backup-your-databases/)). Its changelog lists the failure modes worth learning from. Version 2.0.7 fixed "a Borg archive gets created even when a database hook fails", and 2.0.0 made `after` hooks run "even if an error occurs first" so cleanup is reliable ([borgmatic NEWS](https://raw.githubusercontent.com/borgmatic-collective/borgmatic/main/NEWS)).

Taken together, the prior art points to one contract. The service declares **commands**. The platform owns **transport, layout, encryption and order**. A save that exits non-zero, or produces nothing, yields **no snapshot**. Restores **fail closed**, unlike Velero's `Continue`. Every hook has an **explicit timeout**. The quiesce/unquiesce step **always runs and is told the outcome**. Streaming is preferred whenever the engine's format allows it. The strongest objection is that per-app scripts are error-prone: Cloudron and Coolify avoid them, and StartOS moved to typed builders. Coolify's alternative is also fragile, though: it backs up a database only if the container carries the expected environment variables, such as `POSTGRES_PASSWORD` ([Coolify](https://coolify.io/docs/databases/backups)). Under Angee's ownership rule, the typed library already exists in the right place: the service template. A Postgres template written once is Angee's `withPgDump`, and no database knowledge needs to enter Go.

## Five databases, five different restore preconditions

The engines agree on almost nothing beyond one point: none of them gives a consistent instant *across* databases. Each needs a differently shaped save and a different precondition on restore, so the hook contract must declare both and not assume one.

**PostgreSQL** `pg_dump` "makes consistent exports even if the database is being used concurrently" and "does not block other users" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). Two details matter for Angee right now. First, `--no-owner` and `--no-acl` are **ignored for archive (non-text) output**. For those formats, the docs say, "pass the option to pg_restore instead" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). Angee's current `pg_dump --format=custom --no-owner --no-acl` therefore still captures `ALTER OWNER` statements and GRANTs, and a restore into a stack whose roles differ will fail unless `pg_restore` gets those flags. Second, `pg_restore --list` only "List[s] the table of contents" ([pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)). It shows the header is readable and does not verify the table data. Restore has traps of its own. `pg_restore` by default continues past errors and reports a count at the end, so a hook must pass `--exit-on-error` or `--single-transaction`. Parallel `-j` needs a regular file, not stdin, and cannot be combined with `--single-transaction`. The target should be a database created from `template0`. With `-C`, data goes into the database name stored in the archive, not the one given with `-d` ([pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)). Owners must already exist unless ownership is dropped ([§25.1.1](https://www.postgresql.org/docs/current/backup-dump.html)). Version compatibility runs **forward only**: a dump loads into newer servers but is "not guaranteed" to load into older ones ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). For pgvector, the target image must ship the extension files, and `ALTER EXTENSION vector UPDATE` follows an upgrade ([pgvector](https://github.com/pgvector/pgvector)). Restoring a dump also "causes the destination to execute arbitrary code of the source superusers' choice" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)), which bears on trust below. Physical methods are a different tool: `pg_basebackup`, PITR and pgBackRest 2.60.0 always cover the whole cluster, are tied to one major version, and restore into a stopped server ([pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html), [pgBackRest](https://pgbackrest.org/)). They suit large-data PITR, not a portable "new stack from a snapshot".

**MySQL/MariaDB** `mysqldump --single-transaction` is non-blocking and consistent "only" for InnoDB. Concurrent `ALTER`, `CREATE`, `DROP`, `RENAME` or `TRUNCATE TABLE` break the consistent read, so migrations must not run during a snapshot. Since 8.4, `--all-databases` needs explicit `--routines --events`. The tool is "not intended as a fast or scalable solution" ([mysqldump 8.4](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)). Per-database dumps carry no users. MySQL Shell's `dumpInstance` includes users but writes only to a directory or bucket ([MySQL Shell](https://dev.mysql.com/doc/mysql-shell/8.4/en/mysql-shell-utilities-dump-instance-schema.html)). Physical XtraBackup and mariadb-backup copies must be **prepared**, then restored into a **stopped** server with an **empty** datadir ([Percona](https://docs.percona.com/percona-xtrabackup/8.4/restore-a-backup.html), [MariaDB](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/full-backup-and-restore-with-mariadb-backup)).

**SQLite** is where Angee's live file copy is actively dangerous. A copy taken mid-transaction "might contain some old and some new content, and thus be corrupt". Copying the database without its journal, or overwriting it while leaving a hot journal behind, are both listed ways to corrupt it ([SQLite howtocorrupt](https://www.sqlite.org/howtocorrupt.html)). The WAL "is part of the persistent state of the database" ([SQLite WAL](https://www.sqlite.org/wal.html)). Angee's per-file "did not change during its own copy" check can therefore pass for `app.db` and for `app.db-wal` while the two come from different moments. The safe saves go through SQLite itself: the backup API or `.backup`, `VACUUM INTO` (whose output is "a consistent snapshot", written to a path that must not already exist), or `sqlite3_rsync` ([VACUUM](https://www.sqlite.org/lang_vacuum.html), [sqlite3_rsync](https://www.sqlite.org/rsync.html)). Restore means replacing the file with every connection closed and stale `-wal`/`-shm` files removed. Litestream (v0.5.18, still pre-1.0) restores "only if the output database file does not exist" ([Litestream](https://litestream.io/reference/restore/)), the restore-into-empty rule in miniature.

**Redis/Valkey** is the easy case, by accident. An RDB file "is never modified once produced" and is renamed into place atomically, so "copying the RDB file is completely safe while the server is running" ([Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [Valkey](https://valkey.io/topics/persistence/)). Angee's live copy works for `dump.rdb`, but not for a multi-part AOF directory, which can be swapped by a rewrite mid-copy. Restore happens at startup, and **AOF is loaded in preference to RDB**, so an RDB placed under an AOF-enabled config is silently ignored. Redis 8.10 adds `BACKUP START/SEAL` and a startup-only `preload-file` that aborts if the target is missing ([Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)).

**MongoDB** `mongodump --archive` streams to stdout, but it reflects "a single moment in time" only with `--oplog`, and only on a replica-set member ([mongodump](https://www.mongodb.com/docs/database-tools/mongodump/)). A single-node compose `mongod` should run as a one-member replica set, or its writers should be held. Restore needs a running `mongod` of the same major version or FCV. `--drop` "does not drop collections that are not in the backup". Restoring `admin` replaces users and can leave "an empty database" if authentication then fails ([mongorestore](https://www.mongodb.com/docs/database-tools/mongorestore/)).

| Engine | Save hook (stream or files) | Consistency | Restore precondition | Trap to encode in the template |
|---|---|---|---|---|
| PostgreSQL 18 + pgvector | `pg_dump -Fc` → stdout (or `-Fd` + `-j` as files for large DBs) | one DB, transactional, online | running server; empty DB from `template0`; extension in image | `-O`/`-x` belong on `pg_restore`; add `--exit-on-error` |
| MySQL 8.4 / MariaDB | `mysqldump --single-transaction --quick --routines --events` → stdout | InnoDB only; DDL breaks it | running server; users recreated from secrets | no migrations during save |
| SQLite | `.backup` / `VACUUM INTO` → file | consistent copy of live DB | app stopped; owned dir emptied | never copy `.db` and `-wal` as separate files |
| Redis / Valkey | `BGSAVE`, then copy `dump.rdb` → file | point-in-time RDB | server stopped; no AOF dir shadowing | AOF wins over RDB at startup |
| MongoDB 9.0 | `mongodump --archive --gzip [--oplog]` → stdout | one moment only with `--oplog` | running `mongod`, same major/FCV | `--drop` keeps collections absent from the dump |

Across services, PostgreSQL's own wording sets the honest standard: per-database snapshots "are not synchronized" ([§25.1.2](https://www.postgresql.org/docs/current/backup-dump.html)). MongoDB promises only "approximately the same moment" for sharded snapshots ([MongoDB](https://www.mongodb.com/docs/manual/core/backups/)). The only engine-agnostic way to get coherence across services is to stop the *writers* (the app services) for the length of all saves, which is BBR's all-locks-first phase. No source prescribes the post-restore order, but the version rules imply it: restore data, run engine post-steps such as `ANALYZE`, migrate forward, and only then start apps.

## Restoring into an empty target is the industry default

Managed platforms almost never overwrite in place. RDS says it flatly: "You can't restore from a DB snapshot to an existing DB instance". To swap, you rename the original first ([RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_RestoreFromSnapshot.html)). DigitalOcean always restores to a new cluster, because restoring into the existing primary "would create multiple database timelines" ([DigitalOcean](https://docs.digitalocean.com/products/databases/postgresql/how-to/restore-from-backups/)). Fly restores by creating a new volume with `--snapshot-id` ([Fly](https://docs.fly.io/volumes/snapshots)). Kubernetes provisions a new PVC from a `VolumeSnapshot` `dataSource` ([Kubernetes](https://kubernetes.io/docs/concepts/storage/volume-snapshots/)). Render tells users to "Only restore exports into an empty database" ([Render](https://render.com/docs/postgresql-backups)).

App platforms reach the same result through "provision fresh, then hydrate". YunoHost refuses to restore an app that is already installed, re-provisions resources from the *archived* manifest, then runs the archived restore script ([YunoHost backup.py](https://github.com/YunoHost/yunohost/blob/HEAD/src/backup.py)). StartOS models restore as an init step of kind `'restore'` ([StartOS](https://github.com/Start9Labs/start-technologies/blob/master/projects/start-sdk/lib/backup/Backups.ts)). Home Assistant installs the recorded app version, wipes the data and config folders, and copies the backup back in ([HA Supervisor](https://github.com/home-assistant/supervisor/blob/main/supervisor/apps/app.py)). Cloudron offers clone and import, and its full-server restore requires matching versions ([Cloudron](https://docs.cloudron.io/backups/)). Charmed PostgreSQL's "migrate a cluster" means deploying fresh, scaling to one unit, setting the old passwords, then restoring by `backup-id` ([Canonical](https://canonical-charmed-postgresql-single-kernel.readthedocs-hosted.com/14/how-to/back-up-and-restore/migrate-a-cluster/)). Velero restores into a new namespace with `--namespace-mappings`, and by default "will never overwrite data that already exists in your cluster" ([Velero](https://velero.io/docs/main/restore-reference/)). "Init a new stack from a snapshot" is therefore not an extra feature. It is the normal shape of restore.

Where in-place restore exists, it comes with a safety valve. Heroku's restore "deletes all data from the target database" ([Heroku](https://devcenter.heroku.com/articles/heroku-postgres-backups)). Neon keeps the prior timeline as a `{branch}_old_{timestamp}` branch ([Neon](https://neon.com/docs/introduction/branch-restore)). Railway keeps the old volume, unmounted ([Railway](https://docs.railway.com/reference/backups)). Proxmox overwrites only with `--force` ([qmrestore](https://pve.proxmox.com/pve-docs/qmrestore.1.html)). restic warns that an interrupted in-place restore "can leave files in a partially restored state" ([restic](https://restic.readthedocs.io/en/stable/050_restore.html)). The engines add a reason to prefer an empty target even when restoring in place. `pg_restore --clean` drops only "the objects that will be restored" ([pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)), and `mongorestore --drop` keeps collections absent from the dump ([mongorestore](https://www.mongodb.com/docs/database-tools/mongorestore/)). A logical restore over live data therefore leaves behind anything created after the snapshot, such as tables from later migrations. Emptying the owned state first makes in-place and new-stack restore the same operation.

Two restore inputs are not data. **Secrets** come first. Juju keeps credentials out of backups on purpose, and migration requires setting the old passwords before restoring ([Canonical](https://canonical-charmed-postgresql-single-kernel.readthedocs-hosted.com/14/how-to/back-up-and-restore/create-a-backup)). StartOS resolves database passwords only after volumes are restored ([StartOS](https://github.com/Start9Labs/start-technologies/blob/master/projects/start-sdk/lib/backup/Backups.ts)). Angee's own proposal notes that Django-encrypted fields need the original `SECRET_KEY`. **Side effects** must wait. Supabase warns that `pg_cron`/`pg_net` jobs "start running as soon as the restore completes" ([Supabase](https://supabase.com/docs/guides/platform/clone-project)), and Velero injects a restore-wait init container so that apps do not start before their data is back ([Velero FSB](https://velero.io/docs/main/file-system-backup/)). There is also a **trust** tension. Angee's proposal says restore "must never execute ZIP-provided shell commands", while YunoHost and Home Assistant run or install exactly what the archive records. The way through is authenticated storage. restic authenticates every file with Poly1305-AES under the repository key ([restic design](https://restic.readthedocs.io/en/stable/100_references.html)). A snapshot from the stack's own repository is then as trustworthy as the manifest that wrote it, while an unencrypted ZIP from anywhere is not.

## restic is the only engine that owns storage and nothing else

restic 0.19.1 (2026-07-05) is a BSD-2, single-binary Go tool with about 37,000 GitHub stars ([releases](https://github.com/restic/restic/releases), [repo](https://github.com/restic/restic)). Its source tree says it is "a command-line program and not a library", on purpose ([doc.go](https://github.com/restic/restic/blob/master/doc.go)). For a tool whose rule is "shell out to the owner", that is an advantage. The scripting contract is documented. JSON output "is intended to remain backwards compatible". Exit codes are typed: 10 means the repository is missing, 11 a lock failure, 12 a wrong password, 3 an incomplete read, and an unknown code "MUST be treated as a command failure" ([restic scripting](https://restic.readthedocs.io/en/stable/075_scripting.html)). Version 0.19.0 fixed two silent-success bugs: `backup` used to exit 0 when a source path was missing, and `forget` used to exit 0 when it failed to remove snapshots ([v0.19.0](https://github.com/restic/restic/releases/tag/v0.19.0)). **The floor must be 0.19.x.** On streaming, `--stdin-from-command` cancels the backup with "no snapshot" if the command fails, whereas plain `--stdin` "will mask errors" ([restic backup](https://restic.readthedocs.io/en/stable/040_backup.html)). `dump` streams a file out or emits a whole tree as zip or tar, and `restore` has `--overwrite` and `--delete` ([restic restore](https://restic.readthedocs.io/en/stable/050_restore.html)). Verification samples data with `check --read-data-subset` ([restic check](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)). The password can come from `--password-command`, and a repository can hold several keys ([restic repo](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)). Encryption is AES-256-CTR with Poly1305, but the master key can be rotated "only" by `copy` into a new repository ([restic design](https://restic.readthedocs.io/en/stable/100_references.html)). Its weaknesses are operational. "During a prune operation, the repository is locked and backups cannot be completed" ([restic forget](https://restic.readthedocs.io/en/stable/060_forget.html)). A contributor's rule of thumb is about 1 GB of RAM per 7 million blobs ([restic forum](https://forum.restic.net/t/memory-usage-oom-etc-on-a-big-repository/8758)). And restic has no notion of a *set* of snapshots that belong together.

**kopia** 0.23.1 (Apache-2.0) is the serious alternative ([kopia releases](https://github.com/kopia/kopia/releases)). Its genuine edge is maintenance that does not block backups: epoch-based append-only indexes and a single "Maintenance Owner" ([kopia maintenance](https://kopia.io/docs/advanced/maintenance/)). Its supposed advantage for Angee, an importable Go library, is the weak point. No stability promise was found. Velero replaces it with a fork in `go.mod` ([Velero go.mod](https://github.com/vmware-tanzu/velero/blob/main/go.mod)), Kanister pins an unreleased pseudo-version ([Kanister go.mod](https://github.com/kanisterio/kanister/blob/master/go.mod)), and kopia master already declares Go 1.27 ([kopia go.mod](https://github.com/kopia/kopia/blob/master/go.mod)). That is above Angee's 1.25 floor. Embedding kopia also brought FIPS problems into Velero ([Velero v1.19.0-rc.1](https://github.com/vmware-tanzu/velero/releases/tag/v1.19.0-rc.1)). Used as a CLI instead, kopia brings stateful `connect` configuration, a `user@host` identity model, and its own actions, schedules and retention policies ([kopia actions](https://kopia.io/docs/advanced/actions/)). Those features duplicate Angee's orchestration, which the ownership rule forbids.

The strongest argument for kopia is Velero, which added kopia in v1.10 (Nov 2022), made it the default in v1.12, deprecated restic in v1.15, stopped new restic backups in v1.17, and removes restic entirely in v1.19-rc.1, published today ([v1.10](https://github.com/vmware-tanzu/velero/releases/tag/v1.10.0), [v1.12](https://github.com/vmware-tanzu/velero/releases/tag/v1.12.0), [v1.17](https://github.com/vmware-tanzu/velero/releases/tag/v1.17.0), [v1.19.0-rc.1](https://github.com/vmware-tanzu/velero/releases/tag/v1.19.0-rc.1)). Velero's stated reasons are specific to Velero. It described restic as "an inseparable unit made up of a file system data mover and a repository", and wanted to call kopia "through code interfaces" for heavy customisation ([Velero design](https://github.com/vmware-tanzu/velero/blob/main/design/Implemented/unified-repo-and-kopia-integration/unified-repo-and-kopia-integration.md)). Its published benchmark pitted kopia against restic 0.13.1, which predates compression, and the results were mixed: kopia ran **out of memory** on 2 million small files at 1 CPU / 1 GB, where restic finished ([Velero perf](https://velero.io/docs/v1.10/performance-guidance/)). Meanwhile the shell-out pattern keeps working in Go operators. K8up v2.16.1 (Oct 2026) pins restic 0.19.1 ([K8up go.mod](https://github.com/k8up-io/k8up/blob/master/go.mod)). KubeStash refactored its restic integration in February 2026 and called restic its "core backup engine" in July ([KubeStash](https://appscode.com/blog/post/kubestash-v2026.7.10/)). Kanister removed its kopia repository server in August 2026, with no stated reason, while its volume-copy functions still call restic ([Kanister PR #4170](https://github.com/kanisterio/kanister/pull/4170), [backup_data.go](https://github.com/kanisterio/kanister/blob/master/pkg/function/backup_data.go)). The research found no rigorous 2024–2026 benchmark of current versions. The last reproducible one dates from 2022 ([backup-bench](https://github.com/deajan/backup-bench)). The Velero lesson that does transfer is the **cost of switching engines**: in 1.19, old restic-path backups vanish from the cluster view even though the data remains in object storage.

**borg** is out for now. 2.0.0b25 (2026-09-27) is a pre-release ([borg releases](https://github.com/borgbackup/borg/releases)). The project says "do not use for production", and b25 again required new repositories ([borg changes](https://github.com/borgbackup/borg/blob/master/docs/changes.rst)). Stable 1.4.5 is a Python program limited to local and ssh repositories, and it "will keep an exclusive lock on the repository while creating or deleting archives" ([borg FAQ](https://github.com/borgbackup/borg/blob/1.4-maint/docs/faq.rst)). Its natural hook layer, borgmatic, would double-implement Angee, even though borgmatic is the best design reference available.

| Criterion | restic 0.19.1 | kopia 0.23.1 | borg 1.4.5 / 2.0.0b25 |
|---|---|---|---|
| Integration surface | CLI only; documented JSON and exit codes | Go packages without a stability promise; embedders pin forks | Python CLI; borgmatic for hooks |
| Overlap with Angee's hooks | none | actions, schedules, retention policies | borgmatic |
| Concurrency | non-exclusive backup locks; **prune blocks backups** | epoch indexes; maintenance does not block | exclusive lock on create (1.4) |
| Streaming dumps | `--stdin`, `--stdin-from-command`, `dump` | `--stdin-file` | `--content-from-command`; borgmatic FIFOs |
| Release status | 0.x, repo format v2 since 0.14 | 0.x, past format break at v0.9 | 2.0 beta, repo-breaking in b25 |
| Go operators on it in 2026 | K8up, KubeStash, Kanister volume copy | Velero (forked) | none found |

## Recommendation: three owners, one pipeline

The design comes down to three owners. **Templates own the commands**, because they know their engine. **restic owns the bytes**: repository, crypto, dedup, retention, verification. **Angee owns the order**: holds, the hook sequence, the commit point, secrets first, apps last. Nothing below asks Angee to dump a database itself, implement a storage format, or schedule a second job engine.

### Terms: a singular `snapshot` group and an `init --from-snapshot` flag

Use the noun **stack snapshot** for the whole record and **member** for each per-service part. The **snapshot repository** is where they live. Each service declares a **save** and a **restore**. The command group is singular, `angee snapshot`, to match `job`, `secret`, `service` and `source`. The creation verb is `create`, as in `kopia snapshot create`, `neon snapshots create` and AWS `CreateDBSnapshot`. Removal is `forget`, not `delete`, because restic's `forget` drops the record and frees space only at `prune`; calling it `delete` would promise something the owner does not do. Create-new-from-snapshot belongs on the existing `angee init`, following Velero's `--from-backup`, Fly's `--snapshot-id` and RDS's restore-into-new-identifier. The REST routes become `/snapshots`, with `/backups` kept as a deprecated alias for one release, and the admin-bearer boundary stays as it is.

| Command | Effect | restic underneath | Precedent |
|---|---|---|---|
| `angee snapshot init` | create the repository; print an offline recovery key | `init`, `key add` | `restic init` |
| `angee snapshot create [--hold web,worker]` | run all saves, copy unowned persist paths, write the manifest member last | `backup --stdin` per stream member, `backup <paths>`, manifest via stdin | kopia/Neon `create`, Heroku `capture` |
| `angee snapshot list` | complete stack snapshots only | `snapshots --json --host <stack> --tag angee.kind=manifest` | `restic snapshots` |
| `angee snapshot show <id>` | members, sizes, start/end times, images | `snapshots --json --tag angee.snapshot=<id>`, `stats` | `pg:backups:info` |
| `angee snapshot restore <id> --force [--keep-old] [--only databases/app]` | in-place restore (below) | `dump … \| restore job`, `restore --target` | Heroku restore, Neon `_old_`, Proxmox `--force` |
| `angee init [path] --from-snapshot <repo>#<id>` | new stack from a snapshot | same pipeline, new root | Velero `--from-backup`, Fly `--snapshot-id` |
| `angee snapshot export <id> -o stack.zip` | decrypted portable file, flagged sensitive | `dump -a zip` | `restic dump`, Render "Create export" |
| `angee snapshot forget <id>…` / `prune` | drop records / apply retention and reclaim space | `forget`; `forget --keep-*` then `prune` | restic |
| `angee snapshot check [--read-data 5%]` | verify stored data | `check --read-data-subset` | `restic check` |

### Manifest: services own a paired save and restore, run as ordinary jobs

The declaration moves from the job (`capture:`) to the service (`snapshot:`). The save and restore *point at* ordinary jobs, so runtime, image, env, mounts, receipts and redaction all reuse the existing `JobBackend`, with no second job engine. `owns:` replaces `exclude_persist`. An owned path is never copied as files, because the save reproduces it, and Angee empties it before restore. That one field makes the restore target always empty. `persist.<name>.snapshot: exclude` replaces `backup: exclude` for state that is unsafe to copy and owned by no save. `stream` means the job's stdout is the artifact on save and its stdin on restore. `files` keeps today's staging-directory contract for formats that need a directory or a file path. `requires` encodes the engine's restore precondition.

```yaml
snapshots:
  repository: ${secret.snapshot_repository}  # any restic URL: /srv/snapshots, sftp:…, rest:…, s3:…, b2:…
  password: snapshot_password                # secret name; restic reads it via --password-command, never argv
  hold: []                                   # writers stopped during every create; hot by default
  retention: {keep_daily: 7, keep_weekly: 4, keep_monthly: 6}   # becomes restic forget --keep-*

persist:
  pgdata:  {subpath: postgres/data, scope: stack}            # owned by db below: never file-copied
  appdb:   {subpath: app/db, scope: stack}                   # owned by app below
  media:   {subpath: media, scope: stack}                    # unowned: restic copies the files
  scratch: {subpath: tmp, scope: stack, snapshot: exclude}   # was backup: exclude

services:
  db:
    runtime: container
    image: pgvector/pgvector:0.8.7-pg18
    snapshot:
      group: databases
      name: app
      owns: [pgdata]             # was exclude_persist; emptied before restore
      save:    {job: db-save, stream: app.pgdump}                    # stdout → one restic member
      restore: {job: db-restore, requires: running, timeout: 30m}    # db started alone, then stdin ← member
  app:
    runtime: container
    image: ghcr.io/example/app:1.4                                   # ships sqlite3
    snapshot:
      group: service_state
      name: app-db
      owns: [appdb]
      save:    {job: app-db-save, files: [app.db]}                   # written under ${inputs.snapshot_output}
      restore: {job: app-db-restore, requires: stopped}              # runs before app starts

jobs:
  db-save:
    runtime: container
    image: pgvector/pgvector:0.8.7-pg18
    env: {DATABASE_URL: "${secret.database_url}"}
    command: ["sh", "-c", "exec pg_dump --format=custom --dbname \"$DATABASE_URL\""]
  db-restore:
    runtime: container
    image: pgvector/pgvector:0.8.7-pg18
    env: {DATABASE_URL: "${secret.database_url}"}
    command: ["sh", "-c", "exec pg_restore --no-owner --no-acl --single-transaction --exit-on-error --dbname \"$DATABASE_URL\""]
  app-db-save:
    runtime: container
    image: ghcr.io/example/app:1.4
    mounts: ["bind://${persist.appdb}:/data", "bind://${inputs.snapshot_output}:/out"]
    command: ["sqlite3", "/data/app.db", ".backup /out/app.db"]
  app-db-restore:
    runtime: container
    image: ghcr.io/example/app:1.4
    mounts: ["bind://${persist.appdb}:/data", "bind://${inputs.snapshot_input}:/in:ro"]
    command: ["cp", "/in/app.db", "/data/app.db"]
```

The sketch fixes both Postgres defects: the ownership flags move to `pg_restore`, and a failed statement now fails the restore. Because `db` restores into the empty database that the image's entrypoint creates from a fresh `PGDATA`, neither `--clean` nor `-C` is needed. That is the StartOS `initdb` + `pg_restore` pattern. A template for a large database switches to `files` with `pg_dump -Fd` and `pg_restore -j`, and accepts plaintext in the 0700 staging directory for the duration. Jobs named by `snapshot.save` or `snapshot.restore` keep today's capture-job rules: manual only, no `run_on`, never a dependency. Templates must keep owned persist paths to state their save reproduces, since emptying `appdb` also removes anything else stored there. Umbrel's guidance on what is safe to exclude or "dangerous to restore stale" ([Umbrel](https://github.com/getumbrel/umbrel-apps/blob/HEAD/.agents/skills/umbrel-package-app/SKILL.md)) is a ready starting point for that authoring guide. For one release, the strict loader should accept the old `capture:` and `backup: exclude` and translate them: `output` becomes `files: [output]` and `exclude_persist` becomes `owns`.

### Restore: always into empty state, in place only after a safety snapshot

`angee init [path] --from-snapshot <repo>#<id>` is the main path, and it doubles as the only honest verification of a snapshot. BBR's recommended test loop and Coolify's advice to restore into a disposable database both say the same: a restore drill is the real check ([BBR](https://docs.cloudfoundry.org/bbr/bbr-devguide.html), [Coolify](https://coolify.io/docs/databases/backups)). The repository URL and password arrive out of band, from flags, environment or OpenBao, and never from the snapshot itself. Angee reads the manifest member with `restic dump` and shows its restore jobs for review, as `angee init` already shows template inputs, unless `--yes` is given. It then writes the archived `angee.yaml` and template answers into the new root, applying overrides such as name and domain and taking fresh port leases, and writes the **recovery secrets** into the new root's secrets backend before anything renders. Sources and workspaces are materialised next, through the git/jj drivers, from their members. Angee renders the runtime files with every app service down and every `run_on` job suppressed. Each `requires: stopped` restore runs into its emptied owned paths, and unowned persist members come back through `restic restore --target`.

Only then does Angee start each `requires: running` data service on its own, wait for it to report healthy, and pipe `restic dump` into its restore job. Restores fail closed, with explicit timeouts and no Velero-style `Continue`. A normal apply finally brings up the whole stack, and app migrations run forward from the restored schema, the order the PostgreSQL and MongoDB version rules require.

For a stack that must not go down, run this pipeline into a sibling root and switch traffic. That is the restore-beside-then-swap idiom of RDS rename, Heroku `pg:promote` and Neon `finalize`.

`angee snapshot restore <id>` restores the running stack in place, and refuses without `--force`, following Velero and Proxmox. It first takes an automatic safety snapshot tagged `angee.reason=pre-restore`, as YunoHost does before an upgrade. It stops the stack, empties the owned persist paths (or with `--keep-old` moves them to `<path>.pre-restore-<id>`, as Neon and Railway keep the old state), then runs the same pipeline as `init --from-snapshot` (secrets first, owned-path restores, data services alone, apps last) against the same root. A full in-place restore also restores the snapshot's `angee.yaml`. This is Cloudron's and Home Assistant's "revert the code too", and it is the only way to guarantee that the restore jobs match the artifact format. `--only databases/app` restores data alone under the current manifest, and only if that member's group and name are still declared there, which is BBR's "structure matches" check. Either way the result is a restore receipt that records the source snapshot ID as the stack's provenance.

### Engine: restic as a pinned binary behind a thin adapter

Treat restic as a host prerequisite, like process-compose. Pin a minimum of 0.19.1, report it in `angee doctor` via `restic version --json`, and never call `self-update`. Wrap it in an `internal/snapshot/restic` adapter modelled on `internal/git`. The adapter uses `exec.CommandContext` and `--json`, decodes into typed structs that ignore unknown fields, and maps exit codes: 10 becomes "repository missing; run `angee snapshot init`", 11 becomes "repository busy" with `--retry-lock`, 12 becomes "wrong password", and 3 or any unknown code is a failure. The repository is one per destination, with `--host <stack name>` (as K8up uses the namespace). Member paths stay engine-neutral, `/<group>/<name>/<output>`. Tags are `angee.snapshot=<id>`, `angee.kind=member|manifest` and `angee.service=<svc>`. Keeping the layout engine-neutral is Velero's lesson: a future engine switch should not strand old snapshots.

Streaming forces **one restic snapshot per stream member**, so a stack snapshot is a tagged set, and Angee owns one small thing: the **commit point**. Angee keeps running each save job through its existing `JobBackend` and pipes stdout into `restic backup --stdin --stdin-filename`. It does not use `--stdin-from-command`, because that would make restic the parent of the `docker compose` client and bypass the job backend's timeout handling and its `docker rm -f` cleanup. Since plain `--stdin` cannot detect truncation, the **manifest member is written last**, and only once every save job and every restic process has exited 0 and every stream is non-empty (StartOS's 0-byte lesson). The manifest member holds the archived `angee.yaml`, template answers, resolved image references, per-member snapshot IDs with start and end times, and the recovery secrets, all encrypted at rest. Members with no manifest are orphans, forgotten by the next `create`. Holds follow BBR. All holds go first, then all saves, then the release, and the release runs even on failure and is told the outcome. Unowned persist paths go into a single `restic backup <paths>` member. Retention is a thin translation. `restic forget --dry-run --json --tag angee.kind=manifest --keep-*` yields the set of stack snapshots to keep, and members outside it are forgotten. Whoever sets the policy, whether a manifest default or Django per request, restic executes it. `prune` runs as its own operation outside create windows. A small `check --read-data-subset` follows each create, and full rotation runs separately. `export` replaces the self-made ZIP-with-SHA-256 as the only plaintext form, built from `restic dump -a zip` of the members. With restic holding the catalog, Django should mirror `angee snapshot list` rather than keep its own record of which snapshots exist, so the two cannot drift.

### Risks Angee takes on

The first risk is **lost credentials mean lost data**. Every byte is under the repository key, so `snapshot init` must issue a second, offline recovery key with `restic key add`. Rotating the master key means copying to a new repository ([restic encryption](https://restic.readthedocs.io/en/stable/070_encryption.html)). An append-only rest-server can stop a compromised host from deleting history ([rest-server](https://github.com/restic/rest-server)). Second, **prune's exclusive lock** blocks creates while it runs, so the two need scheduling, and stale locks need handling: KubeStash had to add automatic unlocking of repositories left locked by vanished backup pods ([KubeStash](https://appscode.com/blog/post/kubestash-v2026.6.19/)). Third, the **snapshot set is Angee code**. The commit marker, orphan cleanup and retention alignment are where bugs will collect, and the research found no restic guidance for sets. Fourth, **format lock-in**: restic publishes no deprecation policy for repository format v2. The mitigation is engine-neutral layout plus `export`.

Several mechanics are **unverified** and need a spike before the design is final. Does process-compose's foreground `run` pass stdin through to a restore job, as `docker compose run -T` must? K8up's SPDY-to-websocket switch shows how fragile exec streams can be ([K8up releases](https://github.com/k8up-io/k8up/releases)). Does restic accept nested `--stdin-filename` paths? Can several named pipes land in one restic snapshot, as borgmatic does with Borg? If so, a stack snapshot could be one restic snapshot. How costly are many small restic invocations against a remote backend? Finally, the notes did not establish whether restic flags a file that changes while it reads it, so Angee's current per-file stability check must be either kept around the restic copy or dropped on purpose. Memory grows with blob count, and a stack holding very large media trees should test that before relying on the defaults.

## Conclusion

The question looked like a naming choice and an engine choice. The research shows the real design decision is **where the restore target's emptiness comes from**. Once a service declares which persist paths its save `owns`, Angee can empty them, and three problems disappear together. In-place and new-stack restore become one pipeline. Every engine's restore precondition reduces to "running" or "stopped". And the leftovers that `pg_restore --clean` and `mongorestore --drop` can't remove stop mattering. The pieces also fall into place under the ownership rule. Restic's lack of hooks, the trait Velero held against it, is what lets Angee adopt it without double implementation, and the template catalogue, not Go code, becomes Angee's answer to StartOS's typed dump library.

This also changes what "verified" should mean. A hash-checked ZIP or a `pg_restore --list` shows that bytes exist. Only a restore shows that a snapshot works. Making `angee init --from-snapshot` cheap and first-class turns restore drills into a routine anyone can run against a scratch root. The scheduled verification the current design lacks can then be one more stack being created, rather than another checker that has to be built.
